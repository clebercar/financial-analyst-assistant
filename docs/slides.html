Datathon Fase 5 Slide 2 / 14

01 · O que é o projeto

O problema

Analistas financeiros (buy-side) gastam horas lendo um único relatório anual (10-K) de uma empresa antes de recomendar comprar ou vender uma ação. Cada decisão precisa combinar:

  • 📄 Documentos oficiais (10-K e 10-Q da SEC com riscos, demonstrações financeiras)
  • 💵 Preço atual da ação no mercado
  • 📈 Projeções estatísticas (até onde o preço pode ir nos próximos dias)
  • 📰 Sentimento do mercado sobre notícias e earnings calls

A solução

Um agente conversacional (chatbot inteligente) que faz tudo isso automaticamente. O analista pergunta em linguagem natural — "Devo comprar AAPL hoje?" — e o agente:

  1. Decide quais ferramentas usar (RAG, preço, LSTM, sentimento)
  2. Chama cada uma em sequência
  3. Combina as respostas em um resumo coerente
  4. Cita as fontes (qual filing, qual data)

Por que finanças?

O documento do Datathon explicitamente cita "plataformas de ML do mercado financeiro" como referência. Domínio regulado (CVM, BACEN, ANPD) força disciplina em segurança, governança e LGPD — exatamente o que a banca avalia.

Por que reaproveitar a Fase 4?

O LSTM treinado na Fase 4 (previsão de preço da AAPL) virou uma das ferramentas do agente — em vez de ir pro lixo. Isso fortalece a narrativa do pitch: "integrei o trabalho das fases anteriores ao novo sistema".

02 · Glossário rápido

Termos técnicos do projeto, traduzidos pra quem está aprendendo.

🤖 LLM (Large Language Model)

Modelo de IA generativa treinado em texto da internet (ex: ChatGPT, Gemini, Claude). Sabe escrever, raciocinar e seguir instruções. Usamos: Gemini 2.5 Flash via API.

🧠 LSTM (Long Short-Term Memory)

Tipo de rede neural recorrente, boa pra séries temporais (dados em sequência onde a ordem importa). Aprende padrões "longos" que RNNs simples esquecem. Usamos: pra prever preço de AAPL nos próximos 5 dias úteis.

🔍 RAG (Retrieval Augmented Generation)

Técnica que combina LLM com banco de documentos. Em vez do LLM inventar respostas, ele busca trechos relevantes em documentos e gera resposta baseada neles. Usamos: pra consultar 10-K e 10-Q da SEC.

🛠️ ReAct (Reasoning + Acting)

Padrão onde o LLM raciocina sobre o que precisa fazer e age chamando ferramentas externas. Loop: pensar → escolher tool → executar → ler resultado → pensar de novo. Usamos: via LangGraph.

📦 ChromaDB (Vector Store)

Banco de dados que armazena embeddings (vetores numéricos representando texto). Permite busca por similaridade semântica. Usamos: indexamos 300 chunks dos filings.

🎯 Embeddings

Representação numérica de texto (ex: 768 ou 3072 números). Textos parecidos viram vetores próximos. Usamos: gemini-embedding-001 (3072 dimensões).

📊 MLflow

Ferramenta pra rastrear experimentos de ML: hiperparâmetros, métricas, modelos treinados. Resolve "qual versão do modelo está em produção?". Usamos: pra LSTM e classificador de sentimento.

🔭 Langfuse

Ferramenta de observabilidade pra LLMs: registra cada chamada (prompt, resposta, tokens, custo, latência). Usamos: pra rastrear cada chamada do agente.

📏 RAGAS

Framework de avaliação de RAG. 4 métricas: faithfulness (resposta tem suporte no contexto?), answer_relevancy (resposta é relevante?), context_precision e context_recall. Usamos: avaliamos contra golden set de 20 perguntas.

🛡️ Guardrails

Filtros de segurança no input (anti-prompt-injection) e output (anti-vazamento de PII). Usamos: regex no input, Microsoft Presidio no output.

📉 Drift

Quando os dados de produção começam a diferir dos dados de treino — modelo vai degradando. PSI (Population Stability Index) é a métrica padrão. Usamos: Evidently gera relatório offline.

03 · Arquitetura geral

Quando o usuário manda uma pergunta no POST /chat, isso acontece:

USUÁRIO (analista) "Devo comprar AAPL?" │ ▼ ┌───────────────────────────────┐ │ API FastAPI │ │ POST /chat (principal) │ │ GET /health, /metrics │ └───────────────┬───────────────┘ │ ┌─────────────────────────┼─────────────────────────┐ ▼ ▼ ▼ Input Guardrail Agente ReAct Output Guardrail (regex anti-injection) (Gemini 2.5 Flash) (Presidio PII) max length 4096 max_iter=10 │ ┌─────────────┬───────────┼───────────┬─────────────┐ ▼ ▼ ▼ ▼ ▼ consultar prever analisar buscar_em (futuro: _preco _preco_lstm _sentimento _filings mais tools) (yfinance) (PyTorch) (sklearn) (ChromaDB + RAG) ┌─────────────────────────────────────────────────────────────┐ │ OBSERVABILIDADE (em paralelo) │ │ MLflow (modelos) | Langfuse (traces LLM) │ │ Prometheus + Grafana (métricas técnicas) │ │ Evidently (drift report offline) │ └─────────────────────────────────────────────────────────────┘

Fluxo passo a passo

  1. Pergunta chega ao /chat da FastAPI
  2. Input Guardrail roda regex pra bloquear prompt injection (HTTP 400 se suspeito)
  3. Agente ReAct (Gemini 2.5 Flash) decide quais tools chamar
  4. Cada tool executa (yfinance, LSTM PyTorch, sklearn, ChromaDB)
  5. Agente pode chamar mais tools em sequência (até 10 iterações)
  6. Agente compõe resposta final em português
  7. Output Guardrail (Presidio) sanitiza PII se aparecer (email, CPF, telefone)
  8. Resposta sai pro usuário com iterações e tools_chamadas registradas
  9. Em paralelo: Prometheus contabiliza métricas, Langfuse grava trace completo

04 · As 4 ferramentas do agente

Cada tool é uma função Python que o LLM pode invocar. Definidas em src/agent/tools.py.

1️⃣ consultar_preco(ticker)

O que faz: busca o preço atual e a variação dos últimos 30 dias de uma ação.

Como: chama yfinance.Ticker(ticker).history(period="30d").

Retorna: {ticker, preco_atual, moeda, variacao_30d_pct, volume_medio, timestamp}

Exemplo real: AAPL → $280.14 (+12.96% em 30d), volume médio 50M.

2️⃣ prever_preco_lstm(ticker, dias=5)

O que faz: previsão dos próximos N dias úteis usando o LSTM da Fase 4.

Como: carrega models/lstm_torch.pt + scaler.joblib, alimenta últimos 60 dias, prediz autorregressivamente.

Importante: retorna campo aviso quando ticker ≠ AAPL ("modelo treinado apenas em AAPL — previsão experimental").

Limitação honesta: LSTM foi treinado em dados 2018-2024. Se o preço atual está fora desse range (ex: AAPL hoje em $280), o modelo extrapola — qualidade da previsão degrada. Documentado no Model Card.

3️⃣ analisar_sentimento(texto)

O que faz: classifica trecho financeiro como positive / neutral / negative.

Como: pipeline TF-IDF (n-gram 1-2) + Logistic Regression, treinado no dataset financial_phrasebank (Hugging Face).

Retorna: {sentimento, confianca}

Métricas: F1 macro 0.80, precision 0.81, recall 0.80 (test set 691 frases).

4️⃣ buscar_em_filings(query, ticker?, top_k=3)

O que faz: RAG sobre 10-K e 10-Q da SEC indexados no ChromaDB.

Como: embedding da query via Gemini → busca por similaridade no ChromaDB → retorna top_k chunks.

Filtro: aceita ticker opcional pra reduzir ruído (busca só nos filings daquela empresa).

Indexado: 300 chunks (5 empresas × 2 docs × 30 chunks cada). Empresas: AAPL, MSFT, GOOGL, NVDA, META.

05 · Como rodar do zero

Passo a passo pra reproduzir tudo em uma máquina nova. Tempo total: ~30-40 min (a maior parte é download/indexação automatizados).

Passo 1 — Pré-requisitos

Você precisa de:

  • Python 3.11 (instalado via pyenv ou outro)
  • Git
  • Conta no Google AI Studio para a chave Gemini (free tier basta) — https://aistudio.google.com/apikey
  • (opcional) Docker para rodar Grafana + Prometheus juntos

Passo 2 — Setup do ambiente

# entrar no projeto
cd /Users/cleber/projects/postgraduate-machine-learning/phase-5

# criar e ativar venv
python -m venv .venv
source .venv/bin/activate

# instalar dependências (~3-5 min)
make install
python -m spacy download en_core_web_sm
python -m spacy download pt_core_news_sm

Passo 3 — Configurar a chave Gemini

# copiar template
cp .env.example .env

# editar .env: trocar a linha
# GEMINI_API_KEY=sua-chave-aqui
# por
# GEMINI_API_KEY=AIza...sua-chave-real-aqui

Passo 4 — Treinar os modelos (uma vez só)

# LSTM PyTorch — ~30 segundos
make train-lstm

# Classificador de sentimento — ~1 minuto
make train-sentiment

# Confere se artifacts foram criados
ls -la models/
# Esperado: lstm_torch.pt, scaler.joblib, sentiment_classifier.joblib

Passo 5 — Baixar e indexar os filings da SEC

# Indexa no ChromaDB (~20 min, limitado pelo free tier do Gemini: 15 embeds/min)

# Confere

# Esperado: 300

Passo 6 — Smoke test (validar tudo)

# Resultado em evaluation/results/smoke_test.json
# Esperado: 7/7 sucesso

Passo 7 — Subir a API

# Sem Docker (recomendado pra dev)

# API em http://localhost:8000
# Docs Swagger em http://localhost:8000/docs

# Com Docker (com Grafana + Prometheus)

Camada Tecnologia Por que essa
Deep Learning PyTorch 2.x Padrão da indústria, framework do LSTM. Plano original (Fase 4) usava Keras — convertemos pra PyTorch porque o Datathon exige "PyTorch + MLflow" (5% da nota).
ML clássico scikit-learn TF-IDF + Logistic Regression é baseline forte pra classificação de texto, treina em segundos. Cumpre requisito de "modelo baseline com MLflow".

Embeddings gemini-embedding-001 3072 dimensões, multilingual, mesma chave do LLM. Stack consistente.
Vector Store ChromaDB Mais simples que Pinecone/Weaviate, persiste em disco local, sem servidor.
Agente LangChain 1.x + LangGraph LangChain 1.x removeu o create_react_agent clássico. Migramos para langgraph.prebuilt.create_react_agent (function calling nativo, mais confiável que parsing de texto).

Métricas técnicas Prometheus + Grafana Padrão da indústria. Reuso da Fase 4. 4 painéis: rps, latência p95, tokens/dia, distribuição de tools.

Segurança PII Microsoft Presidio Reconhece PERSON, EMAIL, PHONE, CPF, etc. Anonimiza output do LLM.
Avaliação RAG RAGAS 0.4 4 métricas obrigatórias do Datathon. Configurado pra usar Gemini (em vez do default OpenAI).
Container Docker + docker-compose Reuso da Fase 4. Empacotamento + orquestração local de Grafana e Prometheus.
Lint / Type ruff + mypy + bandit Pre-commit hooks. CI no GitHub Actions.

09 · Segurança e governança

Input Guardrail (anti prompt-injection)

Em src/security/input_guardrail.py. Bloqueia ANTES de chamar o Gemini:

  • 7 padrões regex (ex: "ignore previous instructions", "you are now a", "[INST]")
  • Tamanho máximo: 4096 chars (proteção context stuffing)
  • Retorna HTTP 400 com motivo claro

Output Guardrail (Microsoft Presidio)

Em src/security/output_guardrail.py. Sanitiza antes de devolver:

  • Detecta: PERSON, EMAIL, PHONE, CPF, CREDIT_CARD, IBAN
  • Substitui por placeholder (<EMAIL_ADDRESS>, <PERSON>, etc.)
  • Suporta PT (e fallback EN)

10 · Observabilidade

4 ferramentas, cada uma com responsabilidade clara.

📊 MLflow — tracking de modelos

Cada treinamento (make train-lstm ou make train-sentiment) cria um run:

  • Hiperparâmetros (learning rate, hidden_size, epochs, etc.)
  • Métricas (MAE, RMSE, MAPE pro LSTM; F1, precision, recall pro sentimento)
  • Artifacts (modelo .pt e .joblib, scaler)
  • Tags padronizadas obrigatórias: model_name, model_version, model_type, training_data_version, owner, risk_level, fairness_checked, git_sha, phase
# Acessar UI
mlflow ui --port 5000
# Abrir http://localhost:5000

🔭 Langfuse — tracing de LLM

Cada chamada do agente cria um trace na cloud:

  • Prompt enviado, resposta recebida
  • Tokens consumidos (input + output)
  • Custo estimado
  • Latência por tool
  • Sequência completa do ReAct (qual tool, com qual input, qual saída)

Configuração: precisa criar conta grátis em cloud.langfuse.com e setar LANGFUSE_PUBLIC_KEY + LANGFUSE_SECRET_KEY no .env. Se ausentes, traces são desativados (não quebra a app).

📈 Prometheus + Grafana — métricas técnicas

Em src/monitoring/prometheus_metrics.py. Métricas customizadas:

  • chat_requests_total{status} — contador (success / error / blocked_input)
  • chat_tool_calls_total{tool_name} — contador por tool
  • chat_latency_seconds — histograma com buckets [0.5, 1, 2, 5, 10, 30, 60]
  • chat_iterations — quantas vezes o agente loopou

Dashboard Grafana: 4 painéis (rps, latência p95, tokens/dia, distribuição de tools). Provisionado automaticamente em monitoring/grafana_provisioning/.

📉 Evidently — drift offline

Em src/monitoring/drift_report.py. Compara dados de treino vs produção:

  • PSI (Population Stability Index) por feature
  • Threshold: >0.1 warning, >0.2 retrain
  • Output: HTML report + summary JSON em evaluation/results/drift/
# Gerar relatório
make drift
# Abrir evaluation/results/drift/drift_report.html no navegador

11 · O que cortei e por quê

Este é um MVP de 9 dias solo. Tudo abaixo está documentado no SYSTEM_CARD.md com justificativa técnica.

❌ LLM self-hosted com quantização (vLLM/BentoML)

O que pediu: servir Llama-3.1-8B quantizado 4-bit num servidor próprio.

Por que cortei: exige GPU, ~1 semana só pra subir e estabilizar, sem ROI no pitch de 10min.

Mitigação: usamos Gemini 2.5 Flash via API (free tier). No System Card descrevo a configuração vLLM como roadmap.

❌ Champion-challenger retraining automático

O que pediu: retraining agendado com aprovação humana antes de promover.

Por que cortei: exige pipeline robusto + UI de aprovação, não cabe no MVP.

Mitigação: diagrama proposto no SYSTEM_CARD, identificado como próximo passo.

⚠️ Drift retrigger automático

O que pediu: PSI > 0.2 dispara retraining job.

Por que minimizei: sem retraining automático, retrigger não faz sentido.

Mitigação: Evidently roda como script (make drift), gera HTML report. Manual por enquanto.

❌ Feature Store

Por que cortei: nosso projeto tem só 2 modelos (LSTM + sentimento), não justifica overhead. GAP 03 do guia é sobre evitar feature store DESTRUTIVO — nosso "não ter" é decisão consciente, não negligência.

❌ Integration tests end-to-end

Por que cortei: decisão sua. Mantemos só testes unitários (72 deles, todos com mocks).

Mitigação: make smoke faz validação E2E manual antes de release.

⚠️ Cenário 3 do red team (base64 bypass) não bloqueia

Limitação conhecida: nosso input guardrail é regex puro, não decodifica base64.

Mitigação: agente real respondeu de forma segura mesmo assim (não interpretou o base64 como instrução). Roadmap: adicionar decodificação base64 antes do regex.

Filosofia: em vez de fingir que tudo está pronto, escrevemos no SYSTEM_CARD "sabemos que isso é importante, eis como abordaríamos, eis por que ficou fora do MVP de 9 dias". Banca técnica respeita honestidade muito mais do que implementação superficial.
